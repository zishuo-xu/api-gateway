# 设计文档

每个子系统都按「问题 → 方案 → 为什么 → 代价」展开。整体结构见
[architecture.md](architecture.md)，使用方式见 [usage.md](usage.md)。

## 1. 三层限流

**问题**：只有按 Key 限流时，N 个活跃 key 各自都能用满路由的 `upstream_rps`，
合起来就是 N 倍打向上游——配置里的数字保护不了任何东西，上游看到的是总和。

**方案**：一次 Redis Lua 调用原子地检查并扣减最多三个令牌桶：

| 维度 | Key | 容量 / 速率 |
|---|---|---|
| 上游总闸 | `bucket:up:{dim}` | `rps*2` / `rps` |
| 单个 Key | `bucket:key:{id}:{dim}` | `rps*2` / `rps` |
| 客户端 IP | `bucket:ip:{ip}` | `IP_RPS*2` / `IP_RPS`（默认关闭） |

`dim` 通常是路由的上游标识；统一入口 `/v1` 上，上游要等 body 解析完才知道，
所以退化成用前缀命名——粒度粗一些，但不会抢在 proxy 之前误报 404/400。

**为什么必须一个脚本**：三个桶若分三次调用，两个并发请求可能各自通过了
自己那一项检查，然后一起把上游打超。原子性是这个设计成立的前提。

脚本分两趟：第一趟只计算每个桶补充后的令牌数，记录第一个不够的桶；
第二趟统一 `HMSET` 持久化。**被拒时补充量照样落盘**——
否则一个桶会在第一次耗尽的瞬间冻结住，再也不填充。

**为什么拆成三种拒绝原因**：`rate_upstream`、`rate_key`、`rate_ip` 的处置方式
完全不同（加容量 / 压这个 key / 找那个吵的地址）。混成一个 "rate limited"
等于每次限流都要重新排查。

**代价**：桶容量是速率的 2 倍，允许短时突发。要更平滑就得调小这个倍数。

## 2. 响应缓存

**只缓存 GET**，且请求 `Accept: text/event-stream` 时整条链绕过缓存包装——
流式响应会被 `captureWriter` 吞住，直到结束才吐给客户端，流式就没意义了。

**模型列表不缓存**。它随调用方的 key 变化（受限 key 不该看到自己用不了的模型），
而且计算很便宜——正确性优先于省一次聚合。

**归属（scope）是最容易出事的地方**：

- `global`（默认）：键只有 `method+path+query`，所有 key 共享一份
- `key`：键前面加 `key{id}:` 前缀，每人一份

对天气、汇率这类公开接口，global 是特性（省上游调用）。
但会返回**用户私有数据**的路由必须改成 `key`，否则第一个调用方的响应
会被发给下一个提问的人。

**不缓存流式响应**：它没有有意义的终点，重放等于喂给客户端一段
过时且可能被截断的事件序列。

**代价**：`cache_ttl` 传 0 会被当作 30 秒，不是关闭缓存。

## 3. 熔断

**方案**：按上游（渠道）计数，`cb:{upstream}:fail` 累加失败次数，TTL 30 秒；
累计到 5 次就把 `cb:{upstream}` 置为 `open`，TTL 10 秒。
一次成功则两个键都删掉，立即恢复。

这是**简化版状态机**：没有显式的半开态，靠 10 秒 TTL 到期自动放行，
成功即清零，失败重新计数。

**为什么全熔断时还要试**：`orderedChannels` 在所有渠道都跳闸时，
会退回完整列表而不是直接 503。拿到一个真实的上游错误，
比网关自作主张短路要有用得多——前者告诉你上游确实挂了，
后者可能只是网关的状态过期了。

**代价**：阈值（5 次）和恢复时间（10 秒）是写死的常量，
不同上游的容忍度不一样时无法分别调。

## 4. 多渠道故障转移

**排序两阶段**：先按 `priority` 升序稳定排序分层，
再在每一层内部按 `weight` 做加权洗牌。

加权洗牌用 **Efraimidis-Spirakis** 算法：给每个渠道算
`k = u^(1/w)`（u 是随机数，w 是权重），按 k 降序排列即得到无放回的加权排列，
O(n log n)，不需要反复重试去重。

**什么情况换渠道**：

```go
code >= 500 || code == 429 || code == 408
```

即 5xx、上游限流（429）、上游超时（408）才重试。
**其他 4xx 不重试**——400/401/403/404 意味着请求本身或凭证有问题，
换一个渠道只会得到同样的结果，白费上游额度。

429 值得单独说：它是上游**限流**，换一个不限流的渠道是有效的解法，
所以归入可重试。这与"4xx 不重试"并不矛盾，区别在于失败原因
是「请求错了」还是「这条路暂时走不通」。

**请求体重放**：重试时 `r.Body` 已经被读干了，直接重发会带着空 body，
把「渠道 A 挂了」变成一句让人困惑的上游 400。
所以入站 body 会被 peek 到内存并在重试时重新提供。

**代价**：peek 意味着大请求体会进内存。上限由 `peekBody` 的 limit 控制。

## 5. 用量与计费

**问题**：非流式响应直接读 JSON 就能拿到 usage。流式是 SSE，
provider 通常**不返回 usage 事件**——不处理的话每个流式调用都按一个固定单位计费。

**方案**：挂一个 `usageSniffer` 的 `io.Writer` 装饰器，
在转发的同时逐行扫描，从 chunk 里还原 token 数。

细节：

- 按 `\n` 切行解析，缓冲区上限 256 KB，超了只保留尾部
  （usage 帧很小且出现在末尾，不可能被截掉）
- **同时支持 SSE 与 NDJSON**：`data:` 前缀的是 SSE，
  裸 `{` 或 `[` 开头的是 NDJSON。这个判断是安全的——
  SSE 每行都以字段名开头，永远不会以 `{` 或 `[` 起始，
  两种形态不可能混淆。只认 SSE 的那段时间里，NDJSON 帧被整段丢弃，
  流式请求被静默记成 0 token。
- 可选注入 `stream_options.include_usage`（`INJECT_STREAM_USAGE`，默认开）
  让 provider 补发最终 usage 事件

**记录哪些量**：prompt / completion / total tokens，
TTFT（首 token 延迟），tokens/s，
以及 prompt cache 的**命中**与**写入** token。

前两项好理解。prompt cache 那两项的意义在于：
「为 4 万输入 token 付费」和「为 4 万输入 token 付费但只花十分之一」
是截然不同的成本结构，这正是热 agent 循环与冷启动之间成本的主体差异。
Anthropic 只对写入收费（约 1.25 倍），只有它上报 `cache_write`。

## 6. 配额

**问题**：每请求 `UPDATE api_keys` 会把写事务放到热路径上，
并且把同一个 key 的并发请求串行化。

**方案**：Redis `INCRBY` 计数（原子且便宜），
同时把 key 加进 `quota:dirty` 集合；后台定时器每 `QUOTA_FLUSH_SEC` 秒
（默认 10）把脏 key 写回 Postgres。

**写成功后才从脏集合移除**，这样一次短暂的数据库故障会在下一个周期重试，
而不是静默丢掉用量。

**冷启动水合**：Redis 里没有计数器时从 Postgres 读 `quota_used`，
用 **SetNX 而不是 Set**——并发请求里赢的那个装上持久化值，
其余的在它基础上继续累加，而不是把它重置掉。

**代价**：Postgres 里的 `quota_used` 最多滞后一个刷新周期。
启动时 `SyncAllKeys` 会用这个值预热，所以重启是从上次的位置继续，
而不是重新发一份额度。

## 7. 审计与指标

**审计**投递进带缓冲的 channel（默认 1024），后台单条异步 INSERT。
不在热路径上等数据库。

**指标**用一次 Redis Pipeline 写完所有计数器——热路径上逐个 INCR
意味着多次网络往返，延迟会被放大几倍。

写两类：

- 累计：`stats:total` / `stats:cached` / `stats:rejected` / `stats:errors`
- 每秒序列：`stats:sec:{sec}` 及其 cached / rej / err 变体，TTL 70 秒（图表窗口 60 秒）

**代价**：审计是异步的，进程被 `SIGKILL` 时缓冲区里那批（最多 1024 条）会丢。
配额在 Redis，不受影响。

## 8. 凭据处理

`mwAuth` 认证通过后会把 `X-API-Key` 和 `Authorization` **两个头都删掉**，
不是只删认证用的那一个。

原因是有些客户端会把两个头都设上。只删赢的那个，剩下的那个会被转发到上游，
provider 收到调用方的网关 key 并返回 401 Invalid API key——
而网关这边明明已经认证通过了同一个请求。

真正想自带上游凭证的调用方用 `X-Provider-Key`，这个头原样透传。

## 9. SSRF 防护

运行时配置下游路由意味着用户可以填任意 `base_url`，
网关可能变成打内网的跳板。校验在 `validateRoute` 里，
拦掉 `localhost`、`0.0.0.0`、`::1`、私有网段，
以及云元数据地址 `169.254.169.254`。

## 10. 路由热加载

路由表在进程内存里，管理接口改完走 `reloadRoutes()`：
换掉本副本的内存表，再递增 Redis 的 `routes:version`。

其他副本的 watcher 有两个触发条件：

1. 版本号动了 → 立即重载
2. 周期性强制重载（默认 5 分钟）→ 兜底 Redis 计数器丢失，
   以及运维直接改 SQL 的情况

版本号在启动后、第一次 tick 之前就先读一次做种。
同伴可能正好在我们启动读库和第一次检查之间递增了计数器，
种晚了就会漏掉那次变更。「从读不到变成读得到」也算变更——
计数器要么刚被创建，要么是同伴在我们启动时动的，重载都是安全的答案。

**Redis 只是门铃，Postgres 才是事实来源。**
计数器丢了最坏结果是重载慢一点，不会读到错的路由。
